## 一、拿官方 App

### 1. 官网给的是死链，镜像站给的是假版本

**现象**：学校二维码扫出来的 APK 直链 404。只能去第三方镜像站下，页面标称 v1.9.0，装上一看功能对不上。

**真因**：静态分发早没人维护了，镜像站只抄了标题没换包。

**定位**：不看页面文字，看包本身。

```bash
aapt2 dump badging app.apk | head -3
# package: name='com.yicheng.hnustkb' versionCode='...' versionName='1.7.7'
```

**教训**：所有"从哪下载"的信息都不可信，只信 `versionName` + `versionCode` + 包名三件套。版本对不上，后面逆出来的接口字段很可能也是错的——这次是运气好，1.7.7 与目标版本接口一致。

## 二、登录时

### 2. 密码必须 RSA 加密，明文一律「解密失败」

**现象**：v1.0.0 直接把明文密码 POST 上去，服务端回：

```
解密字符串[4514]时遇到异常
```

`4514` 这个数字很关键——它比明文长得多，说明服务端拿到的东西跟你想的不一样。

**真因**：服务端先把密码**剥掉前 7 个字符**再解密，而那 7 个字符正是加密方案的前缀 `__RSA__`。你发明文，它剥掉的是你密码的前 7 位，剩下自然解不开。

**定位**（这是整个项目最有价值的一次排查）：

1. 拿假密码连发两次，长度不同，观察报错里露出的残段长度；
2. 反推"固定少了 7 个字符"这条规则；
3. 去 CAS 网页源码里找 `__RSA__` 和 JSEncrypt，坐实加密方式为 `RSA/ECB/PKCS1Padding`；
4. 公钥来自 `GET /cas/jwt/publicKey`（标准 PEM，RSA-2048）。

**修法**：

```
password = "__RSA__" + Base64(RSA_PKCS1(明文))
```

对应代码：`hnust.py: rsa_encrypt_password`、`HnustClient.java: encryptPassword`。

### 3. 同一个坑引出的两个误判

**(a)「密码是不是有长度限制？」——没有。** 现象是有时候报解密失败、有时候报密码错误，看着像截断。实际全是加密与否的差别：加密路径走通就到校验环节，不加密就死在解密环节。**两个完全不同的错误码被同一个表象掩盖**，这是那半天最大的时间黑洞。

**(b) openssl 手工验证加密方案，怎么试都不对。** 命令行输出 base64 里带 `+`，塞进 URL 查询参数后 `+` 被解码成空格，服务端拿到的密文已经烂了。修法就一句：`encodeURIComponent` / `urllib.parse.quote` 之后才能拼进 URL；或者用 `openssl ... -A` 输出单行再整体编码。

**教训**：报错信息里的数字（`[4514]`）是最硬的证据，别当噪声跳过；跨进程传 base64 一律先 URL 编码。

## 三、找课表服务（弯路最长的一段）

### 4. 服务列表「获取失败null」：缺三个设备头

**现象**：token 是合法拿到的，调门户服务列表接口却返回 `获取失败null`。`null` 不是"没数据"，是服务端某个取值为空。

**真因**：官方 App 每次请求都带三个设备信息头，缺一个服务端就查不到上下文：

```
X-Terminal-Info
X-Device-Info
X-Device-Infos
```

**定位**：抓官方 App 的完整请求，跟自己的请求做 header diff。别猜字段名，diff 一遍就都有了。

### 5. `packagename` 不是安卓包名

**现象**：设备头补上了，还是失败。设备头里有个 `packagename` 字段，填 `com.yicheng.hnustkb` 不认。

**真因**：这个字段要的是 uni-app 的运行时 ID：

```
__UNI__AA068AD
```

**教训**：字段名叫 package，不代表填包名。名字是弱提示，值是硬约束——去官方请求里抄，不要按字面理解。

### 6. 服务列表不是平铺的，课表还藏在二次解析里

**现象**：以为是一层数组，遍历找 name 含"课表"的项，找不到。

**真因**：

- 结构是 **9 个分组 / 47 个服务**，顶层没有课表；
- 课表在「教学服务」这个**聚合服务**里，子项用下划线键名（如 `xs_kcb`）；
- 聚合项的内容不是对象，是**一段 JSON 字符串**，要再 `JSON.parse` 一次。

**连带坑**：里面大量服务的地址是相对路径或 H5 链接，直接拼接口域名就抛 `no protocol`——**v1.0.1 就栽在这**。

**修法**：解析分两步，先按分组找聚合项，再对内容做二次解析；拼 URL 前先用 `new URL(base, href)` 或 `urljoin` 归一化，别用字符串加号。

### 7.「课表地址」不是接口地址

**现象**：从服务列表里扒到看起来像课表入口的链接，直接当 API 调，返回的是登录页 HTML。

**真因**：那是个 **CAS 登录链接**（带 `service=`），不是接口。真正的教务接口在另一个域名：

```
http://kdfw.hnust.edu.cn/bbxyhd      # 本部
http://xxfw.hnust.edu.cn/xxxyhd      # 潇湘
```

而且**只有 http，https 不通**，App 必须显式开明文流量（Android `usesCleartextTraffic="true"`）。

### 8. 猜子域名，全白猜

**现象**：试过 `study-i`、`jwxt-i`、`kcb-i` 一类命名，解析全失败。

**真因**：学习中心的地址在官方 APK 里是**运行时占位符**，配置从服务端下发，静态分析永远找不到。

**教训**：命名规律是给人看的，不是给 DNS 看的。找不到地址时，优先找"地址是从哪来的"，而不是枚举可能性。

## 四、认证时（连栽四次）

### 9. 教务接口不认门户 token

**现象**：把门户拿到的 `idToken` 用四种方式传给教务接口，全部 401「非法访问」：

| 传法 | 结果 |
| --- | --- |
| `X-Id-Token` 请求头 | 401 |
| `userToken` Cookie | 401 |
| `?token=` URL 参数 | 401 |
| `token` 请求头 | 401 |

**真因**：一直在传**错的凭证**。教务系统有自己独立的一套 token，跟门户的 idToken 毫无关系。四种传法本质是同一次错误重复了四遍。

**教训**：401 连挂四次时，该停下来怀疑"凭证本身错了"，而不是继续换传递方式。**同一假设的多种变体不是多次验证。**

### 10. 教务 token 藏在 sessionStorage 里

**现象**：翻遍所有接口响应、所有 Cookie，都找不到那个 token。

**真因**：它**不出现在任何接口响应里**。CAS 登录后 `loginSso` 跳转到 H5 落地页，token 挂在**落地 URL 的参数**上（188 字符），页面自己把它写进 `sessionStorage`。

**定位**：教务 H5（`http://kdfw.hnust.edu.cn/bbxy/`）的静态文件公开可下载，逆它的 JS：

- `serverconfig.json` 里有 `ApiUrl = http://kdfw.hnust.edu.cn/bbxyhd`；
- axios 拦截器里一句 `headers.token = sessionStorage.getItem("Token")` —— 这条线就是这么接上的。

**修法**：关掉自动重定向，手动跟 302 链，在每一跳的 `Location` 里找 `token=`；沿途把教务 host 的 `JSESSIONID` 一并存下。

```
CAS → loginSso?ticket=ST-xxxx → 落地页?token=<188字符>&userType=...&toMenu=...
```

**教训**：`localStorage` / `sessionStorage` 是前端凭证的常见落脚点，H5 的 JS 比接口文档可信一百倍。

## 五、调接口时

### 11. 接口名双胞胎：`getSycurriculum` vs `curriculum`

**现象**：登录成功、周次正确、页面一片空白。最难查的一种——所有中间状态看着都对。

**真因**：

| 接口 | 用途 | 行为 |
| --- | --- | --- |
| `/student/curriculum` | 课程表页 | 返回完整课表 |
| `/student/getSycurriculum` | 首页小课表 | 同样参数，返回「当前周次未查询到课表！」+ 一堆空数组 |

**v1.0.10 用了后者**，症状因此极具迷惑性。两个接口参数一模一样，只有名字差几个字母。

**教训**：`code` 是 `"1"`（成功）不代表有数据。空数组要在解析层显式报"该接口不适用于此场景"，别静默渲染成空白。

### 12. 拉课表前必须先取作息模式 ID

**现象**：`curriculum` 也返回空。

**真因**：要先调 `POST /Get_sjkbms`，从返回的 `data` 里取 `mrms == 1`（默认模式）的 `kbjcmsid`：

```
0B841F8A531A4C05BE8DB7DB4B40AEF1
```

这个 ID 是必填的，取错或空着都拿不到课。取到后缓存复用，不必每次重取。

### 13. `classTime` 是紧凑数字串

**现象**：课表能拿到，但课程块画在了错误的行上。

**真因**：`classTime` 不是 `"3-4"`，是 `"0304"` 这种紧凑串；长课时是 `"03040506"`。没有真实响应样本之前只能靠猜格式，各学期格式还不完全统一。

**修法**：两两切片取起止，兼容中文写法：

| 输入 | 解析结果 |
| --- | --- |
| `0304` | 3–4 节 |
| `03040506` | 3–6 节 |
| `第3-4节` | 3–4 节 |
| `0909` | 9 节（单节） |

相邻且同课（同名、同教师、同地点）的块自动合并成整块，否则长课会被切成两个视觉碎片。

**教训**：字段格式只能靠真机样本校准。看到"位置不对"先怀疑解析，别怀疑渲染。

## 六、做界面时

### 14. 弹窗里的 WebView 打不进字

**现象**：把登录页塞进 `Dialog` 里的 WebView，点输入框弹不出键盘，账号密码根本输不进去。

**真因**：对话框窗口本身拿不到输入焦点，焦点事件传不到里面的 WebView。改 `windowSoftInputMode` 也没用。

**修法**：改成**全屏覆盖层**（`FrameLayout` 叠在 Activity 上），焦点链正常。这一版后来被无头登录整体取代——现在登录页是原生表单，不再依赖 WebView 输入。

**教训**：WebView 对容器很挑。对话框、`PopupWindow`、部分 `BottomSheet` 都是雷区。

### 15. 登录成功的落地检测失灵

**现象**：登录明明成了，人却卡在学校 H5 页面里出不来。就是你吐槽「和我自己用科大 App 看有什么区别」那次。

**真因**：落地判定只认了教务域名落地这一种情况，实际跳转落到了 `/bbxy/` 路径，没被识别成"已登录"。

**修法**：判定条件从"域名匹配"换成"URL 里出现 token 参数"——token 才是登录成功的唯一硬证据。再加一层兜底：超时后不管落在哪，只要拿到了 token 就放行。

**教训**：**用结果判成功，别用路径判成功**。路径会变，凭证不会。

## 七、流程上的

### 16. 日志功能自己出过 bug

**现象**：出问题时导出日志，文件是空的。排查等于盲人摸象，只能靠猜。

**真因**：异常在写日志之前就抛出去了，`try` 块根本没走到记录那行。

**修法**：改成**先记后抛**——`catch` 里第一件事是写日志，第二件才是 `throw`。关键路径（登录、取 token、拉课表）都在 `finally` 里补一条出口日志。

**教训**：日志系统本身也需要被测。一个默默吞掉日志的 logger 比没有 logger 更危险——它让你误以为"这里没问题"。

### 17. 我自己的两个想当然

**(a) 以为服务列表里会有现成的课表接口。** 实际课表藏在聚合服务的二次解析里（见 #6），中间隔了三层：分组 → 聚合项 → JSON 字符串。

**(b) 以为一个 token 能通吃全校系统。** 门户、教务、学习中心各有一套凭证，互不认（见 #9、#10）。

**这个项目最大的教训**：学校这套系统里**任何假设都得回到官方 App 的源码 / 请求里验证**。猜的成本比查高得多——猜一次要写代码、跑、看错误、改，查一次只是 diff 一下 header 或 grep 一下 JS。

### 18. 假账号测通了，不等于登录通了（补记）

**现象**：APK 装到真机上，账号密码确认无误，仍然一直提示「账号或密码错误」。

**真因**：我提交的 CAS 表单和浏览器真实提交有四处差异，其中致命的是 **POST 的 URL 上少了 `?service=`**：

| 项 | 浏览器 | 修之前 |
| --- | --- | --- |
| POST 地址 | `/cas/login?service=…` | `/cas/login` |
| `failN` | `0`（页面脚本把初始的 `-1` 改成了本地失败次数） | `-1` |
| `submit1` | `Login1` | 没发 |
| `fpVisitorId` | 32 位 FingerprintJS 指纹 | 空 |
| `rememberMe` | **不发** | 发了 `false` |

**为什么之前测不出来**：密码错的时候，服务端在「校验凭证」这一步就返回了，**永远走不到用 `service` 签发票据那一步**。所以拿假账号测一百次，缺 `service` 也看不出来——它只在密码正确的成功路径上爆炸。而密码错和流程错，服务端返回的是同一句「账号或密码错误」。

**定位方法**：

1. 用无头浏览器把真实登录走一遍，**把 POST 的完整 URL、每个字段、每个请求头都抓下来**（之前只对了字段，没对 URL）；
2. 逐项 diff，发现 URL 少了 `service`、`failN` 应该是 `0`；
3. 找一个「能判成功」的探针：`/token/password/passwordLogin` 会明确返回 `401 Bad credentials`（密码错）或 `200 + idToken`（密码对），而 CAS 表单页对两种情况都只说「密码错误」；
4. 起一个本地 mock CAS（自签 RSA 密钥），断言请求形状 10 项不变量 + 解密后密码一致 + 302 拿 token，连成功路径一起测。

**修法**：POST 也带 `service`；`failN=0`；补 `submit1`；去掉 `rememberMe`；`fpVisitorId` 用持久化的 32 位随机值；补 `Origin`/`Referer`。

**教训**：**用一个只能失败的凭证做验证，等于只测了失败分支**。任何"请求形状"类的假设，都要有一条能走通的成功路径来证明——没有真账号，就自己造一个 mock。

### 19. 「登录失败」不一定是登录失败

**现象**：v1.0.2 在你手机上一直提示密码错误。加日志导出后，第一份日志就把真相摊开了：

```
POST /cas/login?service=...        -> 302 (0B)
GET  /bbxyhd/loginSso?ticket=***   -> 302 (0B)
GET  /bbxyhd/loginSso;jsessionid=*** -> 200 (348B)
S 未取到 token，跳转 2 跳
E 登录被拒，页面提示：（未识别）
```

**真因**：CAS 返回 `302` = 票据已签发 = **学号密码是对的**。错在下一步。真机的落地页不是「地址栏里带 token 的 302」，而是 `200` 的 348 字节小页面——token 要么写在 HTML/JSON 里，要么页面只是一段用 `script` 拼出下一步地址的中间页（Spring 的 `;jsessionid=` 就是它生成的）。旧代码只在 URL query 里找 token，找不到就统一报「登录失败，请检查学号与密码」，把人往改密码的方向带。

**修法**：

1. **token 认四个来源**：地址栏 → `Location` → `Set-Cookie` → 响应体（正则兜 `?token=`、`"token":"…"`、`token:…` 三种写法）。
2. **跟「软跳转」**：`location.href=` / `location.replace(` / `window.location=` / `meta refresh` 都当跳转处理，最多 12 跳，每跳记一行日志。
3. **用状态码判性质**：CAS 回 302 却拿不到 token 时，报「统一认证已通过，但教务系统没交出 token」，而不是「密码错误」。这类错误单列 `kind=sso`，也不计入失败次数——密码是对的，不该触发验证码。
4. **日志记落地页片段**：把那一页压成一行写进日志，任何 32 字符以上的连续串（疑似票据）先打成 `***`。下次落地页再变形，一眼能看出它长什么样。

**教训**：

- **错误信息要指向下一步动作**。「密码错误」让用户去改密码，「落地页没交出 token」让开发者去看那 348 字节。同样是登录失败，第二句才可执行。
- **先看状态码，再猜原因**。`302` 和 `200` 是两种完全不同的失败，混在一起就成了玄学。
- 顺手记一笔：v1.0.2 里那个「密码探针」`passwordLogin` 这次回的是 `400`（之前是 `401`）——**探针自己也会变**，它的结论只能当参考，不能当铁证。真正硬的证据是 CAS 到底有没有签发 302。

## 四条可复用的判断

1. **报错里的数字是证据**——`[4514]` 反推出了"剥 7 字符"。
2. **401 连挂就换假设，别换姿势**——四种传法都是同一个错误。
3. **用结果判成功，别用路径判成功**——token 在就算成了，落在哪个 URL 不重要。
4. **只能失败的凭证，测不出成功路径的 bug**——缺 `service` 这种错，假账号永远发现不了。
